# OnebotNoa 实现笔记

本文件记录**已实现系统的行为与边界**，作为 [DESIGN.md](DESIGN.md)（最初的设计建议）的落地对照。
上手步骤见 [README](../README.md)，配置项见 [config.example.yaml](../config.example.yaml)。

> 设计文档写的是"打算怎么做"，本文件写的是"实际怎么做的、以及为什么在若干处与设计不同"。

## 1. 连接方向命名

设计文档用"正向/反向"，实现统一改为按**谁拨号**命名——这两种说法在不同实现端的
文档里含义相反，是最容易沟通出错的地方：

| 名称 | 谁发起 | 中继角色 |
|---|---|---|
| `upstream_listen` | QQ 实现端 → 中继 | WebSocket 服务端 |
| `upstream_dial` | 中继 → QQ 实现端 | WebSocket 客户端 |
| `downstream_listen` | Bot → 中继 | WebSocket 服务端 |
| `downstream_dial` | 中继 → Bot | WebSocket 客户端 |

## 2. 与设计文档不同或更细的地方

### 2.1 身份识别是五级，不是三级

设计文档写"三级兜底"。实现里第 4、5 级是运维必需：

1. 预绑定 token
2. `X-Self-ID` 头
3. 首帧 `self_id`（`identity_timeout` 内）
4. 未知账号策略 `pending` / `reject` / `auto`
5. **串号检测**：同一 `self_id`、不同 token 指纹 → 拒绝 + 审计

第 5 级挡的是"两个账号用同一个 `self_id` 接入"这种会把事件投递到错误 Bot 的故障。

### 2.2 事件转发是字节级原样

设计文档提到"不改写"，实现把它作为硬约束：路由只需要 `post_type`/`self_id`/`group_id`
等少量字段，转发用的是**读到的原始字节**。绝不做解析→再序列化的往返，否则会丢未知
字段、改数字精度、打乱键序。

### 2.3 本地应答必须在目标解析之后

设计文档把"本地应答"列为一组可以直接回答的 action。实现中发现顺序错了会破坏语义：
**绑定多个账号的 Bot 调 `get_status` 没有唯一答案**，必须返回 1404，而不是替所有
账号作答。因此顺序固定为：解析目标 → 拒绝歧义/未授权 → 本地应答或转发。

`LocalActionHandler` 的签名带上已解析的 `selfID`，服务只对确定的那一个账号作答；
`get_status` 只报告该账号（多账号共用一个 `online` 标志会互相掩盖故障）。

### 2.4 合成帧的 id 必须是 JSON 数字

`lifecycle` / `heartbeat` / `get_login_info` 里的 `self_id` / `user_id` 一律以
`json.RawMessage` 输出数字。用 `map[string]any` + 字符串会序列化成 `"10001"`，
而 NoneBot2 这类框架按整数比较 `self_id`，会静默对不上号。

### 2.5 限速是三层，且只读动作豁免

设计文档的"账号级令牌桶"是一层。实现里共三层（账号级 / Bot×账号级 / 在途并发），
并明确**只读动作（`get_*`/`can_*`/`hub_*`）不计入令牌桶**：查询类调用被发消息的
配额拖慢是很反直觉的运维体验。它们仍计入并发上限。

### 2.6 背压策略从 socket 里抽出来

`drop_oldest` / `drop_newest` / `disconnect` / `block` 实现在一个不依赖 socket 的
`sendQueue` 上，因此可单测。**队列关闭时不 close channel**——生产者可能正处在发送
中途，关掉会变成 "send on closed channel" 崩溃（CI 的 race 检测抓到过）。

### 2.7 HTTP 兼容层里 quick-operation 故意不实现

设计文档把它列为可选。实现里显式返回 **1404 + 说明**：多 Bot 共用一个账号时
"该问哪个 Bot"没有唯一答案，给一个看似可用实则错误的结果比明确不实现更糟。
未开启时该路由根本不存在。

## 3. 独立监听端口的运行语义

- 每个独立监听一个 `http.Server`，**显式 `net.Listen`**，因此端口冲突立刻暴露为
  `runtime=error` + 系统错误信息，而不是启动后才失败。
- 热重建是**增量收敛**：配置未变的监听保持既有 socket 不动；改动或删除的关停并释放；
  新增的立即绑定。WebUI 增删改后无需重启。
- 绑定约束通过 request context 传给共享 handler——独立端口是同一数据平面的
  **更严格视图**，不是第二套实现。

上游独立监听的鉴权约定（排障时最常用）：

| 情况 | 结果 |
|---|---|
| 没有 token | 401 |
| token 有效，但 `self_id` 属于别的账号 | 403 |
| token 属于该账号（或 bootstrap + 正确 `self_id`） | 放行 |

## 4. 关键不变式（改动这块代码时要守住）

1. **挂起表条目的 `release` 恰好执行一次**：限速槽位与并发计数都由
   `removeLocked` 统一归还，超时、回复、流式结束、连接断开都走这条路径。
2. **`write()` 不持写锁调用 `Close()`**：会自死锁。
3. **`sendQueue` 永不 close channel**（见 2.6）。
4. **事件路径不做解析往返**（见 2.2）。
5. **本地应答在目标解析之后**（见 2.3）。
6. **合成帧的 id 用数字**（见 2.4）。
7. **`connect.json` 解析失败绝不覆盖原文件**（见 8.4）：启动失败是可以恢复的，把运维的
   token 抹掉不是。
8. **下发的 Bot 必须带完整策略**：`down_listen.go` / `dial.go` 构造 `hub.Bot` 时要带上
   `RateLimit`/`ActionPolicy`——漏掉字段会让策略静默失效（这是实现过程中真实踩过的坑）。

## 5. 可观测与排障入口

| 入口 | 用途 |
|---|---|
| `GET /metrics` | Prometheus 文本：账号状态、连接数、在途动作、帧/动作/响应计数、限速拒绝、离线队列 |
| `GET /api/v1/events/stream` | SSE 实时事件流 |
| `GET /api/v1/logs` | 流量日志（复用事件环形缓冲，最新在前） |
| `GET /api/v1/audit` | 审计（登录、CRUD、策略拒绝、强制重连等） |
| WebUI「API 调试台」 | 选账号发动作，走完整链路，看原始响应与耗时 |
| WebUI「拨号目标」/「监听端点」 | 出站/入站连接的实时状态、最近错误、下次重试 |
| WebUI「连接文件」 | 查看 / 导出 / 编辑 / 整体导入 `connect.json` |
| 账号页与 Bot 页的「连接信息」 | 直接给出可复制的接入地址与 token |
| `GET /api/v1/connect` | 导出整份文档（备份、迁移） |
| `GET /api/v1/connect/{account,bot}/{id}` | 单个实例的地址与凭据，供脚本使用 |

## 8. 两份配置文件（I10）

最初的实现把连接、账号、Bot、凭据都放在 SQLite 里。改动的原因是运维侧的三个具体问题：

1. **连接表需要被审阅和迁移**：一台机器调通的配置，换台机器只能重新点一遍。文件可以
   `diff`、可以整体复制、可以贴进工单。
2. **数据库损坏会连带拖垮数据面**：管理面（登录/会话/审计）和数据面（连接/路由）挤在
   一个文件里，任何一次写入问题都影响转发。
3. **凭据必须能在界面上再次看到**：拨号要拿明文 token，只存哈希做不到。

现在的划分：

| 文件 | 维护者 | 内容 | 生效方式 |
|---|---|---|---|
| `config.yaml` | 人工 | 监听地址、端点路径、限速/背压策略、日志 | 重启 |
| `connect.json` | 程序生成 | accounts / bots / connections / bindings 及其密钥 | 保存即生效 |
| `connect.json.key` | 程序生成 | 加密 `connect.json` 中 token 的本地密钥（0600） | — |
| `onebotnoa.db` | 程序 | 仅 users / sessions / settings / audit | — |

判断规则一句话：**需要重启的放 yaml，运行中还要改的放 json。**

### 8.1 密钥是"防随手翻看"，不是防拿到整个目录的人

token 用 AES-256-GCM 加密，密钥单独一个文件。这挡住的是：备份、截图、日志、工单里
被顺手看到的明文；以及失去密钥文件后，光有 `connect.json` 也还原不出凭据。

它**不**挡已经拿到整个数据目录的人——那等同于拿到密钥本身。文档里明确写了这一点，
避免形成错误的安全感。

手写的明文 token 会被接受，并在下一次保存时自动加密（`TestHandWrittenPlaintextIsAccepted`）。

### 8.2 连接身份改用 self_id 而不是数据库 id

`DownstreamConn` 的绑定表原本以 account id 为键，现在改为以 `self_id` 为键。理由：
`self_id` 才是线上真正携带的身份，而 id 只是文件里的一行编号——手改文件把它重排之后，
按 id 索引的授权关系会指向错误的对象。

### 8.3 升级不会丢配置

迁移 `0003` 会删掉旧的 `accounts/bots/bindings/listeners/endpoints` 五张表。
执行顺序被刻意固定为：**先读旧表 → 写进 connect.json → 再打开数据库跑迁移**。
反过来写就会先删后读，把运维攒下的配置直接扔掉。`SeedFromLegacy` 只在文档为空时
写入，因此每次启动重复调用是安全的。

### 8.4 编辑文件时的两条保证

- **解析失败绝不覆盖**：`connect.json` 存在但读不通时，`Open` 直接报错并保留原文件。
  "自动修复"一个装着 token 的文件，比启动失败糟糕得多（`TestUnreadableFileIsNotOverwritten`）。
- **写入是原子的**：先写同目录临时文件再 `rename`，崩溃不会留下半份文档。
- **导入先备份**：整体导入前把原文件留成 `.bak`。

### 8.5 已知取舍

- `Import` 期间不能并发读（写锁排他）。这在启动和导入时是可接受的：连接数量是几十级别，
  导入是人工动作。
- 账号的**在线状态**存在内存里，不写回文件。实时状态几秒一变，写回会把一份可审阅的
  配置文档变成日志。
- 独立监听创建后**必须**指定账号：否则那个端口成了不设防的入口。

## 6. 已知边界

- **上游 HTTP 上报是无状态的**：每次上报独立解析身份，"待接入挂起队列"对 HTTP
  客户端不适用（挂起依赖连接生命周期）。
- **拨号目标的出站 token 存在 `connect.json`（本地密钥加密）**：拨号时必须拿到明文才能用，
  所以与"入站 token 只存哈希"不同。它加密存放、与密钥文件分离，但拿到整个数据目录
  的人仍可解出。
- **升级是从数据库单向迁移到文件**：没有反向的导入路径，也没有把文件内容写回旧表的工具。
- **中继不解析消息内容**：不做风控、不做内容过滤、不存消息体。需要这些能力应在
  Bot 侧或 QQ 实现端做——中继保持"管道"定位，这样它的性能与行为是可预测的。
- **HTTP API 的 echo 由响应体承载**：WS 上靠 `echo` 关联回包，HTTP 上一个请求一个响应，
  因此中继改写过的 echo 会在返回前还原成调用方自己的值。

## 7. 测试与质量门

- CI 必过：`go vet`、**`go test -race`**、WebUI 构建、单二进制冒烟（`/healthz`）、
  Docker 构建 + 容器探活。
- race 检测在本项目抓到过两个真实缺陷（挂起表计时器竞争导致的自死锁、
  发送队列 close 与 send 的竞争），因此**不要在本地只跑不带 `-race` 的测试就下结论**。
- 跨组件行为（多播、echo 还原、限速共享、背压隔离、独立监听绑定）都有集成测试，
  它们用的是真实的 HTTP/WS 栈而非 mock。
